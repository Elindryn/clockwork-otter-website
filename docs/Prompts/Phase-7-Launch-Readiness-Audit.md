## Project Context

**Two contrast failures already known, from prior phases' own completion reports** (Phase 3h found the first, Phase 3n's Codex review found the second while working on an unrelated component that happens to share the same token — Wolfgang confirmed both are still unfixed before writing this prompt):

- `--navigation-hover` (used for nav and footer link hover states, `var(--color-brand-steel)`) measures **2.62:1** against Foundry Charcoal — below the 4.5:1 WCAG AA minimum for text.
- `--button-secondary-text`/`--button-secondary-border` (the raw `--color-brand-copper`, `#b87333`) measures **3.54:1** against the page background — also below 4.5:1. The secondary `Button` variant currently has **zero live usages anywhere on the site** (confirmed by Phase 3h's own grep) — but it ships broken if any future phase ever uses it, so it's worth fixing now while the pattern for this exact kind of fix (derive a darker/lighter shade via `color-mix()`, matching `CLOCKWORK-BRAND1`'s precedent for the primary CTA) is fresh and already proven to work on this codebase.

**Navigation has no responsive treatment at all.** `Navigation.astro`'s current markup (read the live file — this may have changed since Wolfgang last checked, verify rather than trust this description) is a single fixed `flex` row: logo + 4 nav links, `justify-between`, no wrap behavior, no breakpoint variants, no mobile menu/toggle of any kind. At narrow viewports this will overflow or crush the links together — a real, not hypothetical, accessibility and usability problem, and the brief explicitly requires "accessible mobile navigation" (§17).

**No `prefers-reduced-motion` handling exists anywhere.** All current transitions are simple `transition-colors` (150ms hover fades) on nav/footer links and buttons — no large-scale motion (parallax, auto-play, big movement) exists on this site today. Whether these simple color transitions warrant a `prefers-reduced-motion` guard is a judgment call, not a clear violation — WCAG 2.3.3 targets substantial motion, not hover-color fades. Make the call yourself and explain it (Scope item 1).

## Scope

### 1. Accessibility audit — systematic pass across every public page

Check each item from the brief's §17 against the actual current site (all seven pages: Home, Antiphon, About, Contact, Privacy, Terms, 404):

- Semantic HTML landmarks (`<header>`, `<nav>`, `<main>`, `<footer>` — spot-check these are actually present and correctly nested, not assumed from `BaseLayout.astro`'s structure alone).
- Exactly one `<h1>` per page, correct heading hierarchy, no skipped levels.
- Keyboard-accessible navigation (tab order, no keyboard traps).
- Visible focus states on every interactive element (nav links, footer links, both `Button` variants, the mailto link) — the primary `Button` variant has a custom two-tone focus halo (`CLOCKWORK-BRAND1`/`CLOCKWORK-P3H`); confirm nav/footer links and the secondary button still show a visible focus indicator too, not just primary buttons.
- Sufficient text/background contrast — this is where Scope item 2's two known failures live; also spot-check everything else (body text, headings, the "ANTIPHON" eyebrow, the Privacy/Terms `[TODO]` marker text) rather than assuming only the two known issues exist.
- Meaningful alt text on informative images (the two logo `<Image>` instances currently both use `alt="Clockwork Otter Foundry"` — confirm this is still accurate) and empty/absent alt on purely decorative elements (the Phase 3n watermark is CSS-only, already `aria-hidden`, not an `<img>` — confirm nothing else decorative needs the same treatment).
- No essential information conveyed by color alone (e.g., the active-nav-indicator bar — confirm `aria-current="page"` is also present, not just the visual copper underline; it is, per Phase 3h, but verify).
- Accessible mobile navigation — see Scope item 3, this is the main gap.
- `prefers-reduced-motion` — make and document the call (Project Context above).
- Sufficiently large interactive touch targets (commonly ~44×44px minimum) — check nav links, footer links, both button variants, especially at mobile sizes once Scope item 3 lands.
- Email and navigation links understandable out of context (link text alone, no "click here"/bare URLs) — Phase 6 already grepped for the worst offenders and found none; spot-check again now that this phase may add new links (mobile menu toggle, etc.).
- The nav logo's accessible name — it's wrapped in `<a aria-label="Clockwork Otter Foundry — home">` around an `<Image alt="Clockwork Otter Foundry">`. Confirm (don't assume) that the `aria-label` on the parent `<a>` suppresses double-announcement of the inner image's `alt` text, per standard accessible-name computation — this is exactly the redundant-read scenario the brief's §17 warns about by name.

### 2. Fix the two known contrast failures

- `--navigation-hover`: derive a compliant color from existing brand tokens (don't invent a new hex) — e.g. a darkened/lightened variant of Steel Blue via `color-mix()`, matching the pattern already established for the primary CTA's hover/active states. Show the WCAG math for whatever you land on, against both Charcoal (nav) and the footer's actual background.
- `--button-secondary-text`/`--button-secondary-border`: same approach, derived from Copper. Confirm the fix doesn't collide with or muddy the visual distinction between primary (filled Copper) and secondary (outlined) buttons that `CLOCKWORK-BRAND1` deliberately established — verify hue/darkness still reads as clearly different from the primary fill, don't just chase the contrast number in isolation.

### 3. Build accessible mobile navigation

`Navigation.astro` needs a working small-viewport treatment: a toggle control (hamburger or equivalent) that reveals the nav links, meeting all of:

- Keyboard operable (the toggle itself, and every revealed link, in a sensible tab order).
- `aria-expanded` on the toggle reflecting open/closed state, and an appropriate `aria-controls`/`aria-label` relationship to the menu it reveals.
- Visible focus states throughout, same discipline as Scope item 1.
- Doesn't rely on `:hover` alone (mobile has no hover).
- Adequate touch target size for the toggle itself.
- If you add any open/close transition, apply the same `prefers-reduced-motion` judgment from Scope item 1 consistently.

No specific implementation technique is mandated — a checkbox-driven CSS disclosure, a small inline `<script>` toggling a class/`aria-expanded`, or an Astro client-side island are all reasonable; pick whichever fits this codebase's existing patterns best (this site currently has zero client-side JavaScript anywhere — check whether that's worth preserving as a constraint, or whether a small inline script is acceptable; your call, explain it). Preserve the existing desktop nav exactly as it is — this is additive, not a redesign of the current desktop layout.

### 4. Responsive audit

Across wide desktop, laptop, tablet, and narrow mobile, for all seven pages: confirm the visual hierarchy holds, nothing text-wraps into illegible fragments, no interactive element becomes too small or unreachable, and Scope item 3's new mobile nav actually works end-to-end (not just exists). Body text must not be shrunk below an accessible/readable size to force a layout to fit — if you find a spot where that's tempting, find a structural fix instead and say so.

### 5. Public repository secrets review

Grep the currently tracked working tree (not a full git-history forensic audit — reasonable-effort, not exhaustive) for API keys, tokens, credentials, passwords, private certificates/keys, `.env` files, personal/private notes, or other sensitive configuration. Confirm `.gitignore` actually excludes what it should (check it hasn't drifted since Phase 1/Deploy-1 set it up). Report findings either way — "checked, found nothing" is a valid and expected outcome, not a reason to skip reporting it.
