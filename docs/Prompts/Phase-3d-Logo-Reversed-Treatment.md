## Project Context — read this carefully, it contains analysis Wolfgang already did so you don't have to redo it

**Why 3c is being replaced, not iterated on:** Phase 3b integrated new production logo SVGs and found their black elements (gear + wordmark) measure 1.48:1 WCAG contrast against Foundry Charcoal — a real, confirmed failure. Phase 3c fixed it by wrapping the logo in a white box with a copper border. The user has now decided, directly, that the box is the wrong long-term treatment and wants a proper reversed-color rendering instead — transparent background preserved, only the logo's own colors change. This is a design decision already made, not something to re-litigate.

**The exact SVG structure you're working with** (Wolfgang read all three files in full before writing this prompt — `clockwork-otter-logo-horizontal.svg`, `clockwork-otter-logo-primary.svg`, `clockwork-otter-symbol.svg`, all in `src/assets/images/logo/`):

All three share **identical internal structure and identical element IDs/`inkscape:label` names** for the mark portion — this was originally one mark, reused across all three lockups:
- `#path4-8` (`inkscape:label="BlackGear"`) — the gear silhouette, `fill:#000000`, drawn first (bottom layer). This is the *only* large-area black shape; it's what fails contrast against Charcoal.
- Inside `<g id="g50">`, layered on top of the gear, six white detail shapes (`fill:#ffffff`): `whiteJaw`, `Whitewhisker1`, `WhiteRing2`, `WhiteRing1`, `WhiteHead`, `Whitepupil`.
- Interleaved with those, six small black detail shapes (`fill:#000000`) drawn *on top of* the white shapes: `BlackEye`, `Blackear`, `Blackwhisker1` through `Blackwhisker5`.
- The horizontal and primary (vertical) files additionally contain the wordmark as two more `<path>` elements, `inkscape:label="ClockworkOtter"` and `inkscape:label="Foundry"` — **these have no `fill` set anywhere, inline or inherited from an ancestor `<g>`**, so they currently render via SVG's default fill (black) rather than an explicit value. This matters: it means the wordmark will already follow any CSS `fill` rule applied to the SVG root or a wrapping element, with no inline style to override — the mark's paths, by contrast, all have explicit inline `style="fill:#000000"` / `style="fill:#ffffff"`, which **will** need to be addressed directly (a CSS class or `fill` override targeting each element specifically, e.g. by `id`, since inline styles beat inherited/cascaded rules).

**Why a simple two-way swap should work, not just "make everything light":** if every black element and every white element both became the same light color, the mark would lose all internal detail (solid blob). But look at the actual layering: the gear background is the *only* large black shape; the six white shapes sit on top of it; a few small black details (eye, ear, whiskers) sit on top of *those* white shapes. A **two-class swap** — everything currently black → light (off-white), everything currently white → transparent (or a color that reads as "punched through to the background") — produces a true photographic-negative reversal, not a flattened blob: the gear silhouette becomes a light shape; the six white regions inside it become transparent windows showing the page background through; the small black details on top of those (eye, ear, whiskers) become light again, now visible against the transparent windows. This should read as a coherent "reversed" mark, not a redesign — but **verify this is actually true by rendering it**, don't take Wolfgang's structural read as a guarantee. If it looks wrong (loses the otter's face, reads as a blob, or anything else off), that's exactly the "stop and report" case in Goal/Project Context — don't push through a bad result.

**Recommended colors** (derive from existing tokens, don't invent new hex values): light swap → `var(--color-background)` (`#f7f7f5`, "Warm Off White" — matches the user's own wording "white/off-white" better than pure `--color-surface` white). Transparent swap → literal `transparent` (not a hardcoded Charcoal hex) — this is the more correct reading of "reversed," since it lets whatever's actually behind the logo show through rather than assuming Charcoal specifically, which matters if this logo is ever placed on a different dark background later.

## Scope

### 1. Build a presentation mechanism that controls the SVG's colors via CSS, without editing the canonical SVG files

Per the user's explicit instruction: do not modify `clockwork-otter-logo-horizontal.svg` / `-primary.svg` / `clockwork-otter-symbol.svg` in `src/assets/images/logo/` for this. Instead, create a presentation component (e.g. a new `.astro` component, or a variant/prop on an existing one) that renders the logo **inline** (not via `<Image src={...}>`, which produces an opaque `<img>` tag CSS can't reach inside of — inline SVG in the DOM is required for path-level CSS control). A reasonable mechanism: import the SVG's raw markup (e.g. Vite's `?raw` import suffix) and inject it via Astro's `set:html`, with a CSS class or `id`-based stylesheet rule controlling the known element IDs listed in Project Context. Pick whichever concrete mechanism keeps this maintainable and explain your choice in the completion report — this is implementation-detail latitude, not a scope reduction.

**If you find the actual SVG structure doesn't support this safely once you're looking at it directly** (something Wolfgang's read-only inspection couldn't catch, or the two-class swap genuinely doesn't hold up visually) — stop and report exactly what's blocking it, per the user's explicit instruction. Don't fall back to `filter: invert()` without first stating why direct styling didn't work, and don't fall back to editing the canonical SVGs.

### 2. Nav — reversed logo, no box

Remove Phase 3c's white/bordered container from `src/components/Navigation.astro` entirely. Render the horizontal logo inline with the reversed color treatment, transparent background. Since the box (and its padding/border eating into the 72px header) is gone, you can very likely return to Phase 3b's original 180×45 sizing (which fit cleanly within the header's ~70px content height with real margin, per Phase 3b's own clear-space math) — confirm this still holds, don't just assume it.

### 3. Hero — reversed logo, no box

Same treatment in `src/pages/index.astro`'s hero section — remove Phase 3c's frame, render the vertical logo inline with the reversed colors, transparent background, at the sizes already established before Phase 3c's frame was added (Phase 3b's 160px mobile / 224px `sm:`+).

### 4. Favicon — untouched

`public/favicon.svg` was never part of the contrast problem (browser-chrome context, not Charcoal) and isn't part of this phase.

### 5. Verify

Use the same rasterize-and-measure technique from Phases 3b/3c if a live browser still isn't available in this environment (check first — Phase 3c's environment was worse than 3b's, the dev server itself didn't come up in time; try again, environments can vary run to run). Confirm:
- The now-light gear/wordmark against Charcoal passes 3:1 by a wide margin (expect similar order to the previous white-vs-charcoal 14.16:1 measurement, since off-white and pure white are both very light).
- The reversed mark visually reads as the same otter-and-gear mark, not a flattened shape — describe what you actually see, the way Phase 3b's report did, not just a pass/fail number.
