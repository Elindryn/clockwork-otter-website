## Goal

Fix the confirmed WCAG contrast failure from Phase 3b (the new logo's black elements measure 1.48:1 against Foundry Charcoal, below the 3:1 minimum) by wrapping the logo, in both the Nav and Hero, in a white box with a thin CSS border — recovering full contrast without altering the underlying SVG artwork.

## Project Context

Phase 3b (`docs/Results/Phase-3b-Logo-Integration.md`) integrated three new production logo SVGs and, per its own explicit instructions, did *not* invent a workaround when its live-legibility check found a real problem: the new logo's black gear silhouette and entire wordmark measure **1.48:1 WCAG contrast against Foundry Charcoal (`#2b2b2b`)** — below the 3:1 minimum WCAG 2.2 SC 1.4.11 sets for non-text graphical contrast. White elements are fine (14.16:1). This is currently live on the site (Nav and Hero both), since the old PNG logo has already been deleted.

**Why a white-box treatment is the right fix here, and why it doesn't repeat Phase 2's rejected workaround:** Phase 2's white-card idea was rejected because it would have papered over the *old PNG's* defect — an opaque white background baked into a raster asset that always looked like an unintentional white rectangle, with a real fix (a proper SVG variant) already anticipated and later delivered. This is a different situation: the new SVG artwork is a deliberate two-tone (black/white) mark, and its internal contrast (white otter-face details against the black gear beneath them) is already excellent — the *only* problem is the outer black silhouette's edge against a dark page background. A white box behind the whole mark doesn't hide a defect; it gives the black outline the light background it was evidently designed to be seen against (`03-logo-system.md` itself lists "White" as one of three preferred backgrounds for the primary logo, alongside Charcoal — this treatment satisfies that). The user made this call directly, 2026-08-09, rather than it being an executor-invented workaround.

Relevant files to read before starting:
- `CLAUDE.md` (this repo's root) — Standing Decisions section
- `src/components/Navigation.astro` — current state: `<Image src={logo} alt="Clockwork Otter Foundry" width={180} height={45} />` inside an `<a>` inside a `<header>` with `height: var(--navigation-height)` (`--header-height: 72px`), `border-b` using `--navigation-divider` which is already `var(--color-brand-copper)` — **note this existing precedent**: Copper is already used as a thin structural accent border in this exact header, via `--border-width-medium` (2px).
- `src/pages/index.astro` — current hero state: `<Image src={logo} ... width={224} height={281} class="h-auto w-40 sm:w-56" />` (160px mobile / 224px `sm:`+ ) directly inside the charcoal hero section, above the H1.
- `src/styles/tokens.css` — relevant existing tokens: `--color-surface: #ffffff`, `--color-brand-copper: #b87333`, `--radius-card: 8px`, `--border-width-thin: 1px`, `--border-width-medium: 2px`, `--header-height: 72px`. **No `--border-color-*` token is defined** (flagged as a gap since Phase 1) — do not invent a new one; `--color-brand-copper` is already in active use as a border color in this exact component (`--navigation-divider`), so reusing it here is the consistent choice, not a new invention. Use your judgment if you find a stronger reason to derive a different value via `color-mix()` from an already-approved token instead (Phase 2's precedent for Button tokens), but explain why in your report if you deviate from Copper.
- `../docs/foundations/03-logo-system.md` — Clear Space (25% of gear diameter, every side), Background Usage (White is one of three preferred backgrounds), Incorrect Logo Usage (still forbids altering the underlying artwork — this phase adds a container around it, never edits the SVGs themselves)

## Scope

### 1. Nav — frame the logo

Wrap the existing `<Image>` in `Navigation.astro` in a container: `background-color: var(--color-surface)`, a thin border (Copper is the recommended default per the precedent above — confirm and use, or justify a different derivation), and a corner radius (try `--radius-card`; if that reads disproportionately large at this compact a scale, use your judgment and explain).

**This is the tightest space in the whole site** — the nav bar is a fixed 72px tall, and the header already has its own bottom border. Adding a padded, bordered box around a 180×45 logo has to fit within that 72px without touching the header's top/bottom edges or fighting its own bottom divider. Do the clear-space math (same 25%-of-gear-diameter approach Phase 3b used successfully) accounting for the box's padding *and* border width, not just the logo's own size — you may need to render the logo slightly smaller than 180×45 inside the box to leave genuine breathing room, rather than keeping 180×45 fixed and letting the box overflow or crowd the bar. State your final numbers and the math behind them in your completion report, the way Phase 3b did.

### 2. Hero — frame the logo

Apply the same treatment (white background, matching border/radius approach) around the existing hero `<Image>` in `index.astro`, at both the mobile (160px) and `sm:`+ (224px) sizes already established. The hero has much more room than the nav, so this should be more straightforward — but keep the container styling consistent with what you build for the Nav (same background/border/radius values or tokens) so the two placements read as one visual treatment, not two different ones.

### 3. Favicon — out of scope, do not touch

The favicon (`public/favicon.svg`, added in Phase 3b) was not flagged as a contrast problem — it sits in browser-chrome UI, not on Foundry Charcoal — and is not part of this fix.

### 4. Verify contrast numerically, the way Phase 3b did

Phase 3b's environment couldn't run a real browser (headless Chromium present but missing shared libraries, no `sudo`) and used `sharp` to rasterize each logo at true on-page pixel dimensions, composited onto the real background color, then computed WCAG contrast directly. **Reuse that exact technique** rather than rediscovering it or falling back to "no GUI, can't verify" — check first whether the environment has changed (try the live `npm run dev` + browser route first; only fall back to the rasterize-and-measure technique if it's still blocked). Confirm:
- The black gear/wordmark against the new white box background now passes 3:1 (expect a very large margin, similar order to the existing 14.16:1 white-on-charcoal measurement).
- The internal white-face-vs-black-gear contrast inside the mark itself is unaffected (it doesn't depend on what's behind the whole graphic — this is a sanity check, not expected to change).
- The border color itself is visually distinguishable against both the white box (inside) and the page background (outside) at both Nav (charcoal) and Hero (charcoal) — it doesn't need to hit a formal WCAG ratio since it's a decorative accent, not required content, but it shouldn't be so close in value to either side that it reads as invisible.
