Before ever letting it touch code, evaluate what it actually surfaces: run its `critique` command (UX heuristic review) and its `audit` command (technical a11y/perf/responsive checks) against this site, in **evaluate-only mode — no file edits of any kind**, and produce a written report.

## Project Context

Clockwork Otter Foundry Website is a **live, public, production site** (Astro + Tailwind CSS v4, deployed to `clockworkotterfoundry.com` via GitHub Pages). Its design language, tokens, and brand identity are already fully established and documented in the sibling `../clockwork-otter-brand` repository — this project's own `CLAUDE.md` states explicitly: **"If an implementation decision conflicts with the design system, the design system always wins. Do not invent new branding."** The visual design was deliberately frozen as of the `Polish-1` phase (2026-08-10) — the last content/visual phase before launch.

`impeccable` is a general-purpose frontend design skill, not scoped to this project's conventions. Its own documentation states it treats "refinement" (preserving incumbent identity) and "redesign" (replacing it, treating the old look as "evidence and anti-reference") as genuinely different modes, and that missing design-system files can route it toward treating a project as greenfield. Given this site's design system is emphatically *not* missing and *not* up for reinterpretation, this run exists specifically to see what the tool reports **before** trusting it to write anything.

Relevant files:
- `CLAUDE.md` — Design System Source of Truth section, Standing Decisions (legal-pages text origin rule applies to any UX-copy findings `critique` surfaces)
- `../clockwork-otter-brand/docs/foundations/04-color-system.md` — full color palette, tokens, usage rules
- `../clockwork-otter-brand/docs/foundations/06-design-tokens.md` — canonical CSS custom property names/values
- `../clockwork-otter-brand/docs/foundations/12-website-spec.md` — the original site spec/brief

## Scope

### 1. Setup

Run `node <skill-base-dir>/scripts/context.mjs` once, per the `impeccable` skill's own Setup instructions, with cwd at this project's root. Let it load `PRODUCT.md`/`DESIGN.md` if present; if either is missing, that's expected (this project predates the skill) — do not run `init` or `document` to create them, since those are Build commands and out of scope here. Note in the completion report whether context.mjs reported anything (including a `CONTEXT_STALE` directive) — report it, do not act on it.

### 2. Run `critique` against the site

Target the live site if reachable (`https://clockworkotterfoundry.com`) or a local build/preview if not — see the Verification Steps section below for this project's known `astro preview` binding issue and the fallback. Cover all seven live pages (Home, Antiphon, About, Contact, Privacy, Terms, 404). Record the full heuristic-scoring output.

### 3. Run `audit` against the site

Same target/coverage as above. This checks accessibility, performance, and responsive behavior — areas this project has already run manual/Codex-assisted passes on before (see `docs/Results/Phase-7-Launch-Readiness-Audit.md` and `CLOCKWORK-P3M`'s contrast fixes for prior findings, so you can cross-check whether `audit` re-surfaces already-known-and-fixed issues or finds genuinely new ones).

### 4. Categorize every finding from both commands

For each finding, state: (a) which command produced it, (b) whether it is UX/heuristic or technical/a11y/perf/responsive, (c) whether fixing it would fit inside the existing design-token system as-is, or would require a new token/color/font/pattern the design system doesn't currently have (flag these separately — they are a design-system decision, not a code fix), and (d) your own assessment of whether the finding looks real (verifiable, specific, actionable) or generic/boilerplate advice a tool like this might produce regardless of the actual site.
